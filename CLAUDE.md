# FDH26 — Fête de l'Humanité (non officiel)

PWA mobile-only (React + Vite + TS), fork de l'app PDJ26 (Les Pluies de Juillet) adapté en **application non officielle de fan** pour la Fête de l'Humanité 2026 (91ᵉ édition, 11–13 septembre 2026, Base aérienne 217, Le Plessis-Pâté). Reprend les mêmes features que PDJ26 : plan du site, programme, timeline de favoris avec groupes de copains, rappels de notification, mes billets, FAQ.

⚠️ **Ni développée ni approuvée par l'organisation de la Fête de l'Humanité** — le nom du festival est repris tel quel mais ce n'est pas un produit officiel ; un rappel explicite est affiché dans la FAQ de l'app (« Cette application est-elle officielle ? »), à ne pas retirer. Le site officiel `fete.humanite.fr` est **désormais accessible** (le proxy qui bloquait le domaine ne le bloque plus) : programme, infos pratiques, lieux et illustrations viennent maintenant des **données officielles du festival**, via son flux Chapito (voir « Données »). Les seules données encore issues de la presse sont les **tarifs** (absents du flux), le line-up par vague et le fil d'actualités. Les plans du site affichés dans l'app sont les **plans officiels du festival**, montrés tels quels à titre d'information, chacun avec son avertissement (millésime, zone rognée) — choix explicite de l'utilisateur, qui a remplacé le schéma redessiné des versions précédentes.

## Commandes

```bash
npm run dev        # dev server
npm run build      # tsc -b && vite build (+ génération SW/manifest via vite-plugin-pwa)
npm run preview    # sert dist/ en local
npm run lint       # oxlint
npm test           # vitest run (jsdom) — npx vitest run src/lib/schedule.test.ts pour un seul fichier
```

Régénération des données officielles (dans cet ordre, les scripts se chaînent) :

```bash
python3 docs/tools/build_events.py         # events.json + venues.json + manifeste d'images
python3 docs/tools/fetch_event_images.py   # lit docs/tools/event-images.json
```

Déploiement : le projet a désormais **son propre repo**, `winnieoursbrun/fdh26`, avec son `base` (`/fdh26/`) dans `vite.config.ts`. Le workflow `.github/workflows/deploy.yml` se déclenche sur **push vers `main`** (ou `workflow_dispatch`) et publie `dist/` sur GitHub Pages : **tout push sur `main` met l'app en ligne**. Travailler sur une branche et passer par une PR. Le build passe `SENTRY_AUTH_TOKEN` en secret pour uploader les source maps (`sentryVitePlugin` dans `vite.config.ts`, projet `fdh-react` — **à créer côté Sentry** avant tout déploiement réel, sans quoi l'upload échoue silencieusement ; no-op si le token est absent, ex. en local).

## Architecture

- `src/App.tsx` — shell : header (+ bouton installation PWA), 5 onglets (Carte, Programme, Ma timeline, Prépa, FAQ), tab bar fixe en bas
- `src/tabs/` — `MapTab` (bascule entre les deux plans officiels, zoomables via react-zoom-pan-pinch + légende des lieux par groupe), `ProgramTab` (grille jour/catégorie si `events.json` est rempli, sinon bascule sur `ProgramComingSoon` — line-up annoncé + actus), `TimelineTab` (favoris chronologiques), `PrepTab` (compte à rebours, accès, checklist), `FaqTab` (infos pratiques + FAQ appli, accordéons par catégorie)
- `src/hooks/useFavorites.ts` — favoris = `Set<string>` d'ids, persisté en localStorage (`fdh26-favorites`)
- Groupes de copains (timeline partagée sans backend, spec héritée de PDJ26 : `docs/superpowers/specs/2026-07-08-group-timeline-design.md`) : `src/lib/group.ts` (code de groupe `MOT-NN`, dérivation PBKDF2→AES-GCM + tag, chiffrement), `src/lib/nostr.ts` (4 relais Nostr publics, événements remplaçables NIP-78 kind 30078), `src/hooks/useGroup.ts` (état par membre publié chiffré `{name, favorites, updatedAt, at?}`, fusion par union → `friendsByEvent: Map<eventId, {name, here}[]>`, cache localStorage `fdh26-group*`, identité stable par appareil `fdh26-group-sk`), `src/components/GroupPanel.tsx` (créer/rejoindre, QR via `uqr`, lien `#join=CODE` lu dans `App.tsx`). Dans `TimelineTab`, un bouton « Voir les favoris de mes amis » (actif par défaut) fusionne les événements favoris des amis dans la timeline avec leurs pastilles de pseudo. Présence « j'y suis » : en groupe, un bouton (`PresenceButton` dans `src/components/GroupBadges.tsx`) sur les événements en cours (`isEventOngoing` de `schedule.ts`, horloge `src/hooks/useNow.ts`) publie `at` (un seul événement à la fois, persisté `fdh26-group-at`, fenêtre de 15 min avant le début à 15 min après la fin) ; la pastille d'un ami présent (`friend-chip-here`) passe en jaune avec un pin et en tête de liste. Les relais ne voient jamais le code ni les données en clair.
- `src/hooks/useInstallPrompt.ts` — capte `beforeinstallprompt` ; sur iOS affiche un guide manuel
- Rappels de notification : `eventStartDate()` dans `src/lib/schedule.ts` calcule la date calendaire réelle 2026 d'un événement (même règle de bascule après minuit que `timeMinutes()`) ; `src/hooks/useReminders.ts` programme des `setTimeout` locaux (pas de push serveur, PWA 100 % statique) 15 min avant chaque favori, avec rattrapage au retour au premier plan (`visibilitychange`) et dédoublonnage via `fdh26-reminders-notified` ; état `ReminderStatus` (`unsupported`/`default`/`denied`/`enabled`/`disabled`) piloté par `fdh26-reminders-enabled` ; `src/components/ReminderBanner.tsx` (bannière d'incitation dans `TimelineTab`, une seule fois, `fdh26-reminders-prompted`) et `src/components/ReminderToggle.tsx` (interrupteur dans la section "L'application" de `FaqTab`).
- Mes billets (import local du billet festival) : `src/hooks/useTickets.ts` décode le QR code d'une photo importée via `jsqr` (canvas + `getImageData`, redimensionné à 1600px max) puis ne stocke que la valeur texte décodée sous un libellé libre (`{id, label, value}[]`, localStorage `fdh26-tickets`) — la photo elle-même n'est jamais conservée. `src/components/TicketsCard.tsx` (dans `MapTab`, sous la carte du site) gère l'import, le renommage/suppression et l'affichage plein écran d'un QR régénéré via `uqr`.
- `src/lib/schedule.ts` — constantes jours/catégories (vendredi 11, samedi 12, dimanche 13 septembre 2026), tri chronologique
- `src/lib/sentry.ts` — `initSentry()` (tracing + session replay + logs), appelé depuis `main.tsx`. Comptage des utilisateurs : `getDeviceId()` génère un UUID anonyme stable par appareil (localStorage `fdh26-device-id`), attaché via `Sentry.setUser({id})`.
- `src/index.css` — tout le style, CSS vanilla avec design tokens
- `docs/superpowers/{specs,plans}/` — docs de conception héritées de PDJ26 (contexte, architecture, cas limites, plan de tests) ; à consulter avant de retoucher les groupes de copains ou les rappels

## Données

- **Source unique des données officielles** : le site rend son programme avec le widget **Chapito**, qui charge tout depuis un seul fichier statique — `https://static.humanite.chapi.to/data.json` (repéré via le shortcode `<chapito-static>` du post WordPress `FHU26_PROG_COMPLET`). Les pages HTML « Programme complet » ne contiennent plus rien d'exploitable (rendu côté client) : **ne pas retenter de les scraper**. Le flux publie `events`, `scenes`, `groups` (artistes/stands, avec descriptions et images), `genres`, `poiList` (**coordonnées GPS** de tous les points du site), `infoPratiques`, `sponsors`.
- `src/data/events.json` — **355 événements, les trois jours** (`{id, title, artist, day, start, end, venue, category, subtype, description, recommendations?, speakers?, image?, copyright?}`). Répartition : ven 97, sam 149, dim 109. `ProgramTab` garde ses replis (« Programme de ce jour pas encore disponible » pour un jour vide, bascule complète sur `ProgramComingSoon` si le tableau se vide), mais ils ne se déclenchent plus.
  - Régénération : `python3 docs/tools/build_events.py` (télécharge le flux ; `--data feed.json` pour rejouer une copie locale, `--save` pour la garder). Le script écrit **aussi** `src/data/venues.json` et le manifeste `docs/tools/event-images.json`.
  - **La catégorie est publiée** par le flux (`programId`) : plus rien n'est déduit du lieu. Les huit catégories de l'app sont celles du site (concert, spectacle, debat, conference, cinema, evenement, exposition, atelier) ; un `programId` inconnu fait échouer le script plutôt que de deviner. Les anciennes catégories héritées de PDJ26 (`bal`, `famille`, `balade`, `radio`, `imaginarium`) ont disparu du type `Category`, du CSS (`cat-*`, `chip-*`) et des fixtures de test.
  - `subtype` vient des genres du flux (« Rap », « Électro, Pop », « Débat »), limité à 2 pour rester lisible. `recommendations` est **toujours `null`** : le flux ne tague les sujets (Palestine, Féminisme…) que sur des stands non rattachés aux événements. `EventCard` n'affiche ce bloc que s'il existe, donc rien ne casse s'il se remplit un jour.
  - `speakers` : **les intervenant·es ne sont pas structuré·es dans le flux**, ils sont annoncés dans le texte de `description`. `speakers_from()` les en extrait (**151 événements, 325 noms**) et `EventCard` affiche les noms en petit sous le lieu (`.card-speakers-line`), sans avoir à déplier. Le parseur reconnaît trois formes : `Avec X, Y et Z`, une liste `Nom, fonction ; Nom, fonction` en tête de ligne, et `Animée par X`. Il est **volontairement conservateur** — un nom manquant vaut mieux qu'une fonction ou un média affiché comme intervenant :
    - un nom = 2 à 4 mots capitalisés (un seul mot attraperait « Blast », « Politis ») ; les fonctions commencent en minuscule et sont de toute façon filtrées par `NOT_A_PERSON` (fonctions, collectifs, éditeurs, syndicats), tout comme les suffixes de rôle collés au nom (`ROLE_SUFFIX`, « Sophie BINET SG »).
    - l'extraction est **limitée à `debat` et `conference`** (`SPEAKER_CATEGORIES`) : ailleurs la description est un texte suivi, et l'heuristique « la ligne commence par un nom » y récoltait des phrases (« Originaires de Belfast », « Admiré de Cavanna »).
    - conséquence assumée : les mononymes et les noms cités hors de ces formes sont perdus, et un nom tronqué par le site lui-même le reste (« animée par Pierre-Henri Lab »).
  - Les ids sont des slugs `titre-jour-hhmm` : ils changent si un horaire bouge, ce qui **casse les favoris** correspondants. À garder en tête avant de régénérer. Les doublons (même titre, même jour, même heure sur deux scènes) reçoivent un suffixe `-2`.
- `public/events/*.webp` — **161 illustrations** (1,5 Mo au total), une par événement quand le flux en publie une. Récupérées par `python3 docs/tools/fetch_event_images.py` (`--force` pour tout réencoder, `--prune` pour supprimer les orphelines) depuis `https://static.humanite.chapi.to/images/<id>_square.jpg`, réduites en WebP carré 320 px q72 — il faut qu'elles restent **précachées** (donc petites) pour l'offline. `eventImageUrl()` (`src/lib/images.ts`) fait le mapping id → URL ; `EventCard` les affiche en vignette 60 px (`.card-thumb`, `alt=""` : décoratives à côté du titre) et crédite `copyright` sous la description dépliée.
- `src/data/lineup.json` / `src/data/news.json` — line-up par vague et fil d'actualités issus de la presse, affichés par `ProgramComingSoon`. **Devenus inertes** puisque le programme complet est là ; gardés comme repli.
- `src/data/venues.json` — **33 lieux**, générés par `build_events.py` depuis `scenes` + `poiList`, nommés **exactement comme dans le programme** (le lieu lu sur une carte d'événement doit se retrouver dans la légende — un contrôle le vérifie). Les quatre groupes sont désormais remplis, `bienetre` et `vente` inclus (sanitaires, points d'eau, prévention, boutique). Des libellés saisis à la main dans le back-office sont repliés via `POI_LABEL_ALIASES` (ex. la coquille « Uninoirs féminin », « Village Sport » → « Espace Sport ») ; un point de repère non reconnu comme service rejoint `programmation` plutôt que `accueil`. Un même lieu peut correspondre à plusieurs points relevés sur le terrain (7 « Sanitaires », 6 « Point d'eau ») : ils sont repliés en **une seule entrée** de légende. Quatre lieux du programme n'ont **aucune coordonnée** dans le flux : « Scène Inter - le 92 accueille le monde », « Allées de la Fête », « Stand de Cœur d'Essonne Agglomération », « Village du Livre - Studio Livre » — sans conséquence aujourd'hui, la légende n'étant plus positionnée sur un plan.
- **Deux plans officiels**, chacun incomplet à sa façon ; `MapTab` propose une bascule entre les deux (choix explicite de l'utilisateur) :
  - `public/plan-officiel.webp` (80 Ko, onglet « 2026 ») — extrait du plan de l'**édition 2026**, le bon millésime, mais **rogné sur la droite** (entrée Marcel Cachin, parkings) et portant quelques annotations. Original : `sources/plan-officiel-2026-extrait.jpeg`.
  - `public/plan-2024.webp` (348 Ko, onglet « Vue d'ensemble ») — plan **complet** avec sa légende et les accès, très lisible au zoom… mais c'est celui de l'**édition 2024** : il porte la mention « vendredi 13, samedi 14 et dimanche 15 septembre 2024 », la « Scène Inter - le 92 accueille le monde » (nouvelle en 2026) n'y figure pas et le camping a bougé. L'app le signale explicitement sous le plan. Original : `sources/plan-officiel-2024-complet.png` (4,2 Mo, gardé **hors de `public/`** : il dépassait la limite de précache du workbox et faisait échouer le build).
  - Les deux sont convertis en WebP q85 pour rester précachés (offline) ; `.map-wrapper` porte l'`aspect-ratio` de chacun (`.map-edition`, `.map-ensemble`) au lieu d'une hauteur fixe.
  - Le schéma redessiné `public/map.svg` a été **supprimé**, ainsi que son générateur. Si le besoin d'un schéma original revient (droits, ou un plan 2026 complet à reconstituer), tout est là pour le refaire : `build_venues()` dans `docs/tools/build_events.py` calcule déjà les points géoréférencés (`placements`) à partir des coordonnées GPS du flux.
- La légende de `MapTab` liste les lieux **sans numéro** : les repères du plan officiel ont leur propre codification, un numéro à nous n'y renverrait à rien. Le champ `num` de `venues.json` reste dans les données (il fixe l'ordre d'affichage) mais n'est plus rendu.
- `src/data/faq.json` — **41 entrées** reprises des vraies fiches `infoPratiques` du flux (horaires réels par jour et heures de fermeture des entrées, RER C **et** RER D, navettes, parkings, camping, billets, accessibilité, sécurité/prévention, numéros d'urgence, objets trouvés). La catégorie `Accès & transport` est lue explicitement par `PrepTab.tsx`, ne pas la renommer. Deux réserves : **les tarifs ne sont pas dans les données officielles** (les paliers viennent encore de la presse et sont signalés comme tels dans la réponse), et les fiches officielles gardent des reliquats de 2025 (dates « vendredi 12 septembre ») tranchés en faveur du calendrier 2026. Les entrées de FAQ propres à l'app (dont « Cette application est-elle officielle ? ») restent codées dans `FaqTab.tsx`.
- Adresse codée en dur dans `src/lib/address.ts` (`Base aérienne 217, 91220 Le Plessis-Pâté`) avec lien Maps universel.

Règle de tri importante : les horaires < 05:00 sont la fin de nuit du jour de grille (ex. un set à 00h40 appartient au vendredi) — voir `timeMinutes()` dans `schedule.ts`.

## Design

Identité inspirée de l'imagerie du Front populaire / Fête de l'Humanité : écru `#f2ede2`, rouge `#c8202f`, jaune `#ffd02e`, contours noirs 2px, ombres « sticker » décalées (`--sticker`). Display : Bricolage Grotesque (auto-hébergée via @fontsource, requis pour l'offline). Dark mode via `prefers-color-scheme`. Élément signature : le bouton favori est un **poing levé** qui se lève (`src/components/FistButton.tsx`, classes `.fist-btn`/`.is-raised`/`.fist-glyph`) — clin d'œil au geste de solidarité du festival ; ne pas le remplacer par une étoile ou reprendre le parapluie de PDJ26. Le tracé est l'icône **`hand-fist` de Font Awesome Free 6.7.2** (viewBox `0 0 448 512`), inlinée et exportée en `FIST_PATH`/`FIST_VIEWBOX` (l'état vide de `TimelineTab` la réutilise, classe `.empty-fist`) : **pas** de dépendance npm, pour rester léger et offline. Elle est sous **licence CC BY 4.0**, donc l'attribution de `CREDITS.md` (et du commentaire en tête du composant) est **obligatoire** — ne pas la retirer. Le poing garde la même silhouette dans les deux états (lisible à 44 px), seules la couleur et la hauteur changent : baissé et gris (`--muted`) au repos, brandi et noir sur pastille jaune quand le favori est actif. Retour haptique : `triggerHaptic()` (`src/lib/haptic.ts`, sans dépendance — Vibration API + hack du `<input switch>` pour iOS façon `use-haptic`) est déclenché au tap sur les boutons d'événement favori (`FistButton`) et présence (`PresenceButton`).

L'app doit rester 100 % offline une fois installée : tout asset ajouté doit être précaché (vérifier les `globPatterns` du workbox dans `vite.config.ts`).

## Tests

`ProgramTab.test.tsx`, `TimelineTab.test.tsx`, `useGroup.test.ts` et `useFavorites.test.ts` mockent `../data/events.json` avec une petite fixture locale (`ouverture-ven-1700`, `massilia-ven-2135`, `nocturne-ven-0040`, `village-sam-1000`...) : les tests restent stables quand le vrai programme est régénéré. La fixture n'utilise que des catégories valides du type `Category` — si tu retouches `Category`, `ProgramTab.test.tsx` et `recap.test.ts` sont les deux fichiers à réaligner. `MapTab.test.tsx` vérifie la légende **contre `venues.json`** (donc contre les vraies données) et la bascule entre les deux plans, dont l'avertissement « édition 2024 ». `ProgramComingSoon.test.tsx` couvre l'état "programme pas encore publié" (repli désormais inactif, mais toujours testé).
